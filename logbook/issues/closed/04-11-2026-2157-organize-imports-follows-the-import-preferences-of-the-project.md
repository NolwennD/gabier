# `gabier organize-imports` follows the import preferences of the project

Opened: 04-11-2026 21:57

On a project that already has its import preferences in Eclipse or in VS Code Java, an agent can run `gabier organize-imports`
and get the imports written as that project writes them. Today the daemon imposes the conventions of this repository (no star
import, static imports first, one block) on every project (`JdtlsSettings.javaSection`). The formatter is out of scope.

jdtls reads the import preferences from no file of the project: it takes the `java.*` settings its client sends. The daemon
therefore reads them and sends them, and has no import settings of its own any more:

- `.vscode/settings.json` (JSON with comments): `java.completion.importOrder`, `java.sources.organizeImports.starThreshold`,
  `java.sources.organizeImports.staticStarThreshold`;
- `.settings/org.eclipse.jdt.ui.prefs`: `org.eclipse.jdt.ui.importorder`, `ondemandthreshold`, `staticondemandthreshold`,
  translated to those three keys.

What the files do not set is left to the defaults of jdtls, so a project with no such file gets those defaults (groups `java`,
`javax`, `org`, `com`; star import from 99): a change, said in the `## Resolution`. `filteredTypes`, `templates.typeComment` and
`references.*` stay in `JdtlsSettings`. When the two files give a different value for a key, `.settings` wins and the answer of
the command carries a warning.

This repository declares its convention (the three values it has in `JdtlsSettings` today) in a versioned
`.vscode/settings.json`; `.settings/` is generated by Buildship and ignored.

Done when:
- The jdtls installed is probed first (a throwaway replay): what it does by itself with `org.eclipse.jdt.ui.prefs` and
  `.vscode/settings.json`, written in the `## Resolution`.
- The three import settings are no longer in `JdtlsSettings`; the scenarios of `organize-imports` and of the clean-ups bring
  their own `.vscode/settings.json` where they relied on them (replayed on the real jdtls, effect compared on the files).
- A project with its preferences in `.settings`, then in `.vscode`, gets its order and its thresholds from
  `gabier organize-imports`; a file with only some of the keys leaves jdtls its defaults for the others.
- The two files in contradiction: `.settings` is followed, the text and the `--json` answer of the command carry the warning.
- The files are read again at each request that writes imports, with no restart of the daemon.
- `gabier status` shows the configuration in force, so that a project knows what gabier follows: for each of the three
  settings its value and where it comes from (`.settings`, `.vscode`, or the default of jdtls), in the text and in the
  `--json` answer (`DaemonStatus`), read from the files at the time of the call; it starts no daemon, as today.
- The `.vscode/settings.json` of this repository is committed, and organizing a file of it changes nothing that the
  formatter and Checkstyle accept today.
- `docs/commands/organize-imports.md`, the Javadoc of `JdtlsSettings` and the guide `docs/improve.md` say that the project is
  followed and no longer describe fixed conventions; `bin/ci` is green.

## Resolution

Done in `7be84f9` (pull request 18).

What changed: `JdtlsSettings` no longer holds `starThreshold`, `staticStarThreshold` and `importOrder`. The daemon reads
`.settings/org.eclipse.jdt.ui.prefs` and `.vscode/settings.json` (`ImportPreferences`, `JsonWithComments`; no new
dependency) at each request that writes imports, and sends the three `java.*` settings to jdtls (`JdtlsSettings.imports`).
`.settings` wins on a contradiction, with a warning in the answer of the command (`ChangedFiles.warnings`, text and
`--json`). `gabier status` gives the value and the source of each setting (`DaemonStatus.imports`). This repository
declares its convention (no star import, static imports first, one block) in a versioned `.vscode/settings.json`.

Probe of the installed jdtls 1.63.0: it ignores both files for the imports and reads only the three settings the client
sends; `workspace/didChangeConfiguration` applies from the next request, with no restart; a key absent from a later
configuration keeps its old value, and an empty list does not restore the default order. So the adapter sends all three
settings every time, with explicit values, and for what no file sets, the defaults of jdtls (`ImportSettings.DEFAULTS`:
`java`, `javax`, `org`, `com`; 99; 99).

Why, and what it replaces: the fixed conventions of this repository were imposed on every project
(`JdtlsSettings.javaSection`, the Javadoc and `docs/commands/organize-imports.md`). The decision of the user (04-11-2026):
gabier has no import setting of its own, the project's configuration is followed, and this repository declares its own.
Behaviour change: a project with no file for the imports now gets the defaults of jdtls, star import from 99 included.

Checked (worker's summary): `bin/ci` full, once: format, build, test (cli 873, core 717, daemon 951 + 2 new,
architecture 19), native, jdtls all passed; coverage 100%; the coupling ceilings are unchanged (4 / 5 / 4 / 26); check
`bin-ci` of the pull request green. `organize-imports --dry-run` on 400 `.java` files of the repository: 399 answered
`nothing to change`; `FakeServedMain.java` is refused by jdtls (it cannot resolve the imports of another source set), which

Deviations: the warning is computed in `OrganizeImportsMethod`, which reads `ImportPreferences` itself, not through the

cli. The replay of the scenarios also reads the two settings files; no test was weakened.

`extract-*` and `cleanup` send the settings and say nothing (within the scope of this issue).
