## New in 0.6.0

- **`gabier diagnostics` takes several files and the whole project.** `gabier diagnostics <file>...` asks jdtls for all the
  files in one wait (one file it refuses refuses the whole call); `gabier diagnostics --all` lists every `.java` file of the
  project that has a problem, the tests and the other source sets included, with no file to name, and answers in about a
  second once jdtls is started. Run `gabier help diagnostics`.
- **`gabier diagnostics --watch` follows the problems as files change on disk.** It starts by printing the problems as they
  are, then prints the files whose problems changed after each edit that jdtls has built (`<file>: no problems` for a file
  that became clean), for the given files or, with none, for the whole project. `--json` prints one object per line. It keeps
  running until it is killed, and keeps the daemon from stopping while it runs.
- **`gabier affected-tests` lists the test classes to run again after a change.** `gabier affected-tests <file>...` names the
  tests that depend, directly or through other classes, on the Java files given, whatever the build tool of the project; it
  runs none. With no file it answers for what changed on disk since the daemon's last answer, and `gabier affected-tests
  --watch` keeps running and prints the tests of each series of changes as jdtls builds them. `infinitest.filters` leaves
  tests out. A Java file that does not compile is refused (`testing-compilation-failed`), and so are a missing file, a file
  under no source folder, an invalid filter and a class file that cannot be read. Run `gabier help affected-tests`.
- **`gabier create <file> package` writes a `package-info.java`**, with the package line under
  `@org.jspecify.annotations.NullMarked`. The file must be named `package-info.java` (`editing-not-a-package-info`), and
  its folder must be a package name (`editing-not-a-package-name`).
- **A rename that jdtls fails on is refused as `language-server-request-failed`**, with the code and the message of jdtls,
  where it used to be an `internal-server-error`. Renaming the name of a module in `module-info.java` is refused the same
  way, and its help says it stays a text edit. The refusal ends with the pointer `Usage and other ways: gabier help
  <command>`.
- **The cause of an unexpected failure is in the daemon's log**, `<socket>.log`: the exception, its causes and, for an error
  that jdtls answered, its code and data. The answer to the command is still the generic `internal-server-error`, with no
  description. See [the daemon](https://github.com/NolwennD/gabier/blob/v0.6.0/docs/daemon.md).
- **The MCP server has the new operations as tools**: `diagnostics-all`, `affected-tests` and `affected-tests-changed`
  (`diagnostics --watch` and `affected-tests --watch` are not tools, since a tool answers once; an agent calls `diagnostics`
  or `affected-tests-changed` after each edit). A project reached through a symbolic link is served, there is one lock per
  socket, no two answers carry the same id (a request whose id is that of a call still running is refused with `-32600` and
  a null id), and `status` called right after the handshake, while the daemon is not listening yet, fails with
  `daemon-starting` instead of `daemon-not-running`. See
  [`mcp`](https://github.com/NolwennD/gabier/blob/v0.6.0/docs/commands/mcp.md).
- **The help of a command is its documentation.** The pages `docs/commands/*.md` are removed, except `mcp`: usage, notes
  and refusals are in `gabier help <command>` (and `gabier <command> --help`), and `gabier help --for="<task>"` still
  names the command that does a task.
- Inside: `JdtlsLanguageServer` is split by family of operations (references, renames, moves, inlining, imports, creations,
  diagnostics, code actions) and the `native` stage of `bin/ci` is one launcher and one class per area of checks.
