## New in 0.7.0

- **New: `gabier test` runs the tests and reports the failures.** `gabier test [--timeout=<seconds>] [<test-class>...]` runs
  the test classes given, or, with none, the tests that changed files affect (those `gabier affected-tests` lists), in a JVM
  of their own, on the classes jdtls compiled, with no Maven or Gradle. The answer is the counts (ran, passed, failed,
  skipped) and, for each failed test, its class and method, what was thrown, its message and the first frame in the
  project; `--json` gives the same. The exit code is 3 when some test failed (the report is on the standard output), 0 when
  none did, and 2 or 1 when the call is refused. The MCP server has the tools `test` and `test-changed`; a failing test is
  a result there, not an error. The limit is 300 seconds unless `--timeout` says otherwise. See `gabier help test`.
- **`gabier test` needs the JUnit Platform launcher on the class path of the project.** gabier brings no JUnit: the
  launcher (`org.junit.platform:junit-platform-launcher`) and the engines are the project's own. A project that does not
  declare the launcher (a build that only declares `junit-jupiter`) is refused with `testing-no-test-launcher`, which names
  the dependency. The other refusals are `testing-no-test-engine`, `testing-no-such-test-class`, `testing-test-timeout`,
  `testing-run-failed` and `testing-compilation-failed` (the file of a test to run, or a changed file, that does not
  compile; a file that does not compile elsewhere does not refuse the call, and a test that reaches it fails with
  "Unresolved compilation problem").
- **A restart of the daemon on a project it already opened is ready in about 12 to 14 seconds, not a minute.** The jdtls
  workspace is no longer removed at each stop: it is kept per project in `~/.cache/gabier/jdtls-<version>/workspaces`
  (`GABIER_CACHE` moves the cache), about 210 MB per project or worktree, and removed once the folder of its project is
  gone. `gabier start` and the first command after it are quicker accordingly (`gabier help start`). After Java files
  changed on disk while the daemon was stopped, `gabier diagnostics` answers as after a first start. A daemon or a jdtls
  that was killed, a start that failed, or another jdtls or JDK start again from an empty workspace, as a first start does;
  nothing is cleared by hand.
- **New, optional: an AOT cache for the JVM of `gabier test`.** Start the daemon with `GABIER_TEST_AOT_CACHE=on` in its
  environment (a running daemon keeps the setting it started with: `gabier stop` first) and the tests start about a
  quarter faster (1 s of 4 s on a small class). The first call makes the cache (6 to 8 seconds, about 20 MB, in the cache
  folder of gabier); a cache that cannot be made or used never fails a call. With it on, the jars outside the project
  come first on the class path of the tests, so a project class named like a class of a library is not the one that
  runs. Off by default; see `gabier help test`.
- **The guide knows the new commands.** `gabier help --for="<task>"` answers for running the tests and for starting a test
  JVM faster (`gabier help guide`).
